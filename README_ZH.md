## 本模块做什么

支持硬件密钥认证的 Android 设备都有一个**信任锚**——系统用来校验密钥认证证书链的根证书。多数设备上这个锚点就是 Google 的硬件认证根，而「**额外**信任的 OEM 根证书」列表是**空的**。

本模块让你**把自己的证书填进这个列表**：你选一个 `keybox.xml`，模块提取其中所有证书，并按系统内部的精确命名规范写入 Android 系统信任库。重启后，设备会把这些证书当作**受信任的 OEM 认证根**。

一句话概括：

> **没有本模块** —— 伪装模块签出一条根证书无人信任的链。链本身内部自洽，但验证会失败：*「根证书不受信任」* → **未知根（unknown root）**。
>
> **有本模块** —— 同一个根被加入设备的受信任 OEM 根列表。整条链在本地验证通过，认证状态从「不信任」变为「**本设备信任该根证书**」。

本模块**不触碰**你的 TEE、keystore 或任何证书存储，只是往系统本来就会读取的目录里添加文件。全部由 root 管理器挂载，**完全可逆**。

## 为什么需要它：「未知根」问题

**先做重要澄清，以免预期偏差：**

绝大多数情况下——**包括大多数来自第三方的 RKP keybox，以及泄露的硬件 keybox**——证书链本来就能正常验证，**根本不需要本模块**。Android 设备通常内置信任 Google 的各组认证根（硬件认证根、RKP 根、测试根），因此链终止于这些根上的 keybox，**你的设备本来就会信任**。日常更换 keybox 一般**不会**出现「未知根」报错。

> **本模块是兜底手段，不是必须搭配的组件。**

只有在**少数**情况下，根证书确实不被你的设备信任，它才变得必要：

- **自签名或人工生成的 keybox**：根证书由你自己创建，没有任何设备会信任它。
- **使用非标准或私有 CA 链的 keybox**：链不锚定在你设备信任库中的任何根上。
- **你的设备或 ROM 变体缺少对应根**：例如非 GMS 版本、深度定制的 ROM、特殊区域版本，或信任库被裁剪的较老系统。
- **该根在你的特定固件中已被移除或被认为不可信**。
- **本身有问题的 keybox**：链没有终止于一个格式正确的可信锚点。

在这些情况下，本地密钥认证验证会报出：

- ❌ *「根证书不受信任 / Root certificate is not trusted」*
- ❌ *「未知根 / Unknown root」*，信任锚未知
- ⚠️ 引导程序状态与安全等级可能显示正常，但整个认证不被信任

这正是本模块要解决的问题。缺失的关键只有一点——「**系统应当信任这个根**」，而它是**一个本地列表**，不涉及任何硬件机密。

关键技术事实（已在真机 Android 16 / ColorOS 上核实）：

```text
framework-res.apk → resources.arsc → vendor_required_attestation_certificates
```

这个 `string-array` 存在于 AOSP 的 `framework-res` 中，且多数设备上为**空**。Android 的 `AttestationVerificationManager` 把它当作*额外*受信任 OEM 认证根的集合。**任何**出现在该列表中的证书都会被接受为信任锚——**不做任何远程校验，也不要求任何证明它真的由厂商或 Google 签发的密码学证据**。

本模块按系统标准 CA 命名方案（`<subject-hash>.<n>`）把证书装进系统信任库，这与平台查询信任库的路径一致。结果是：平台现在把你的证书识别为合法信任锚。

## 哪些情况真正需要它（哪些不需要）

### 基线事实：大多数 keybox 本来就能用

先把预期摆正：**大多数 RKP keybox ——包括从第三方或其他设备获取的——以及大多数泄露的硬件 keybox，无需本模块即可在本地正常验证。** Android 设备普遍内置信任 Google 的认证根，因此锚定在这些根上的链开箱即被接受。**如果你换了 keybox 一切验证正常，你根本不需要本模块。**

### 真正需要它的场合

下列情况才是根证书确实不受信任、本模块能改变结果的情形：

| 情况 | 根为何不受信任 | 本模块能否解决 |
|---|---|---|
| **自签名 / 自己生成的 keybox** | 根由你创建，没有任何设备信任 | ✅ 能——最典型的场景 |
| **非标准 / 私有 CA 链** | 链未锚定在你信任库中的任何根 | ✅ 能 |
| **设备/ROM 缺少该根** | 非 GMS 版本、信任库被裁剪、定制 ROM、特殊区域版本、较老且受限的系统 | ✅ 能 |
| **该根在你的固件中被移除或视为不可信** | 具体固件的信任库差异 | ✅ 能 |
| **损坏或异常的 keybox** | 链未终止于格式正确的可信锚点 | ⚠️ 通常能——但 keybox 本身可能才是问题 |
| **普通第三方 RKP keybox** | 根已被信任 | ❌ 不需要——装不装都一样 |
| **真正的 Google 硬件 keybox** | 根已被信任 | ❌ 不需要——装不装都一样 |

### 自签名 keybox —— 最清晰的用例

你自己生成的 keybox（OpenSSL、脚本或「假 keybox」工具生成）的根证书**没有任何设备信任，包括你自己的设备**。

- 没有本模块 → 必然**未知根**
- 有本模块 → 设备在本地信任它，本地验证干净通过

### RKP keybox —— 视情况，并非总是需要

为*另一台设备*预配的 RKP keybox，通常终止于**大多数** Android 设备已信任的 Google RKP 根——这种情况下什么都没坏，本模块没有必要。

只有当你这个特定固件**不带**该根（部分非 GMS 或深度定制系统、某些区域/较老版本），或该 keybox 使用的链未锚定在标准 Google 根集合中时，它才有意义。在这些少数情形下，本模块正好补上缺失的信任锚。

---

### ⚠️ Google 硬件 keybox —— **不建议使用**

如果你持有**真正的、未被吊销的 Google 硬件认证 keybox**（能签出以 Google 硬件认证根为根的链）：

- **没有任何收益**：这条链本来就终止于设备信任的根，把它加进 OEM 列表毫无变化——它从来就不是「未知根」的情况。
- **无法帮助通过 Google 验证**：见[下文](#-本模块做不到什么)。
- **只增加风险**：真实的泄露 keybox 会被广泛比对 Google 的吊销列表，本地信任一个根并不能保护它。

**判断依据：**

| 你的 keybox | 是否该装本模块 |
|---|---|
| 自签名 / 自己生成的 keybox | ✅ **该装——最典型的用例** |
| 根不被你设备信任的 keybox（非 GMS、信任库被裁剪、私有 CA） | ✅ **该装** |
| 普通第三方 RKP keybox | ⭕ **不必**——不装也能用 |
| 真正的 Google 硬件 keybox | ❌ **不必——无效也无益** |

## 兼容性：TEE 模块

本模块与任何 TEE / keybox 伪装模块**并行工作**，因为它在**验证侧**工作（设备信任哪些根），而那些模块在**签发侧**工作（用哪个密钥签链）。

> 注意：大多数 keybox（含第三方 RKP）的根本来就被设备信任，**装不装本模块都能正常验证**。只有根确实不受信任时，才需要用它来补齐。
> Note: for most keyboxes the root is already trusted, so pairing is optional. This module only makes a difference when the root is genuinely untrusted.

| TEE 模块 | 兼容性 | 说明 |
|---|---|---|
| **Oh My Keymint** | ✅ 良好 | 与本模块组合后，根不受信任的链也能在本地验证通过 |
| **TEESimulator** | ✅ 良好 | 天然配对：模拟器负责签名，AnyKeybox 让根被信任 |
| **TEESimulator-RS** | ✅ 良好 | 同上 |
| **Tricky Store OSS** | ✅ 良好 | |
| **Tricky Store** | ✅ 良好 | |
| 其它 keybox / TEE 伪装模块 | ✅ 通常可用 | 只要该模块注入的 keybox 其根证书原本不受信任 |

> **推荐组合**（当根确实不受信任时）：`TEE 模块` + `AnyKeybox - module`
> TEE 模块提供密钥并签出证书链；AnyKeybox 使设备信任这条链的根，从而得到一条**既内部自洽、又在本地受信任**的链。

### 关于把密钥烧录进硬件（烧录）——理论可行，但不推荐

一些进阶用户会问「烧录密钥」进设备（例如把 keybox 预配进安全硬件）。理论上这能产生真正硬件支持的密钥，本模块也就能与之兼容。**但实践中不推荐：**

- 烧录风险高、不可逆、高度依赖具体机型。
- 它本身**并不解决**「未知根」问题——烧录进去的密钥，若根证书无人信任，依然是未知根。（这正是本模块要解决的；但烧录带来的风险远大于修复根信任的收益。）
- 绝大多数用户根本不需要。**请改用「TEE 模块 + 本模块」的组合。**

## 本模块做不到什么

把话说清楚比一味鼓励更重要：

### ❌ 它不能帮你通过 Google 认证 / Play Integrity

本模块让**你的设备**在**本地**信任某个根证书，但它**不会**让**Google 的服务器**信任任何东西：

- Google 的认证校验（Play Integrity 的 `MEETS_STRONG_INTEGRITY` 等）在**服务器端、按 Google 自己的信任库**验证证书链。
- Google 从不读取你设备上的 `vendor_required_attestation_certificates`。
- 无论你的设备本地信任什么，自签名或 RKP keybox 依然无法通过 Google 的服务端校验。

**能否通过 Google 认证，完全取决于你的 keybox 是否真实、未被吊销——与这个模块无关。** 如果你的 keybox 是伪造的、自签名的、或取自其他设备的 RKP，Google 一律拒绝。本模块关注的是**本地一致性**，不是**服务端认证**。

### ❌ 它不是 keybox 生成器

它不生成密钥、不伪造认证链、不修改你的 TEE，只安装你提供的证书。

### ❌ 它无法绕过服务端的硬件验证

任何连接远程服务器、且要求「Google 签发的链」的应用，都会看到真实情况。本地没有取巧办法。

## 工作原理

```text
┌──────────────────┐
│   keybox.xml     │  （任何包含 PEM 证书的 XML）
└────────┬─────────┘
         │  WebUI：提取所有 PEM 块
         ▼
┌──────────────────────────────────────────────┐
│ 按 DER 去重 → 计算文件名                      │
│   name = MD5(Subject DER TLV) → <hash>.<n>   │  ← Android 系统 CA 命名
└────────┬─────────────────────────────────────┘
         │
         ▼
 /data/adb/modules/AnyKeybox_module/
   ├── apex/com.android.conscrypt/cacerts/<hash>.<n>      （优先）
   ├── system/etc/security/cacerts/<hash>.<n>             （回退）
   └── state.txt                                          （记录已导入文件）
         │
         │  你的 root 管理器（KernelSU / Magisk / APatch）
         ▼  以 magic mount 方式挂载进真实信任库
 /apex/com.android.conscrypt/cacerts/<hash>.<n>
         │
         │  Android 的 TrustedCertificateStore 按
         ▼  "<subject-hash>.<n>" 查找，命中你的证书
 ✅ 设备信任该根 → 本地认证链验证通过
```

随后状态引擎会对每张证书执行五步验证（`源文件 → 已挂载 → DER 一致 → Zygote 可见 → 应用可见`），并在 WebUI 中如实呈现，同时判断导入后是否已经重启。

## 功能特性

- **双语界面（EN / 中文）** —— 自动识别系统语言，右上角可手动切换（手动选择会被记住并停用自动识别）
- **明暗主题自适应** —— 跟随系统，右上角可手动切换
- **一键导入** —— 系统文件选择器选取任意 `.xml`；附带手动路径输入兜底
- **完整提取** —— 所有 PEM 块，自动去重；一张都提不出来则明确报错
- **正确命名** —— `<subject-hash>.<n>`，已在真机系统 CA 库上验证 **149 / 149** 全部命中；冲突时 `n` 从 0 递增
- **规范写入** —— PEM 格式、`root:root`、`0644`、SELinux `u:object_r:system_file:s0`
- **双目标检测** —— 优先 APEX conscrypt 信任库，回退 `/system/etc/security/cacerts`，两者都没有则报错
- **真实状态，不靠猜** —— 每张证书五步验证 + 重启判定
- **问题反馈引导** —— 若**重启之后**验证仍失败，UI 提供一键跳转 GitHub Issues（每个开机周期最多提示一次）
- **完全可逆** —— 重新选择即替换旧证书；卸载即清除全部
- **模块简介实时更新** —— 已挂载生效显示 ✅，已导入待生效显示 ⏳

## 安装

**环境要求**：已 Root 的 Android（KernelSU / Magisk / APatch），且管理器支持模块 WebUI。

1. 下载 `AnyKeybox_module-v1.0.0.zip`。
2. 在 root 管理器中安装（KernelSU → 模块 → 从存储安装；Magisk 类似）。
3. 打开模块的 **WebUI**（KernelSU 模块列表中会有「打开 / WebUI」入口）。
4. 选择你的 `keybox.xml`（或任何包含证书的 XML）。
5. 启用模块，然后**重启**（详见 [APEX 与传统路径](#-apex-与传统路径)）。
6. 重新打开 WebUI → 状态卡应显示 ✅ **证书已挂载生效**。

## 如何验证真的生效了

「文件出现在路径上」不等于「系统信任它」。请做真实验证：

### 方式一 —— 内置 WebUI 状态（推荐）

状态卡对每张证书执行五步检测：

| 检测项 | 含义 |
|---|---|
| **源文件** | 模块内的副本存在 |
| **挂载** | root 管理器已把它挂进真实系统信任库 |
| **内容** | DER 指纹与你导入的完全一致 |
| **Zygote** | 在**每个** Zygote 进程的挂载命名空间中都可见 |
| **应用** | 在运行中的应用进程内可见 |

全部通过 ⇒ 该链可本地验证通过。

### 方式二 —— 独立 shell 脚本（仓库内附带）

`verify.sh`（位于仓库根目录，**不在**模块 ZIP 内）可在终端执行同样的检测：

```bash
su -c 'sh /path/to/verify.sh'
# 或显式指定已安装的模块目录：
su -c 'sh /path/to/verify.sh /data/adb/modules/AnyKeybox_module'
```

退出码：`0` = 全部通过，`1` = 存在失败项，`2` = 尚未导入。

### 方式三 —— KeyAttestation 类应用

重启后打开 KeyAttestation 类应用。相关提示不再显示*「根证书不受信任」*，而会变成类似*「本设备信任该根证书，但其他设备可能不信任」*。**这正是本模块追求的状态**——本地受信任，而非全局被认证。

> 若**重启之后**仍失败，打开 WebUI：它会显示每张证书具体是哪一步失败，并提供一键跳转 GitHub 反馈问题。

## APEX 与传统路径

模块自动检测设备使用的信任库，并优先使用现代路径：

| 目标 | 路径 | 生效方式 |
|---|---|---|
| **APEX（优先）** | `/apex/com.android.conscrypt/cacerts/` | **必须重启。** root 管理器在启动时把证书注入 Zygote 挂载命名空间；仅热重载通常不足以让已运行的应用感知。 |
| **系统（回退）** | `/system/etc/security/cacerts/` | **重启或热重载**均可（NoMount 类管理器可热重载）。 |

若两个目录都不存在，导入会以明确错误中止。

> 注意：即使是传统路径，热重载也只影响**新**进程。正在运行的应用仍使用启动时构建的信任库。若某应用仍不信任该证书，请重启。

## 文件命名：`<hash>.<n>`

Android 系统 CA 库以 **`<subject-hash>.<n>`** 索引：

- `<subject-hash>`：证书 **Subject** 的 8 位十六进制哈希（小写）
- `.n`：用于区分**同一 Subject 的不同证书**——`n` 从 0 开始递增

Android（BoringSSL）使用的哈希是：

```text
hash = MD5( Subject Name TLV 的原始 DER 编码 ) 的前 4 字节，小端序
```

这不是猜的，而是**逆向并真机验证**过的：测试设备 `/apex/com.android.conscrypt/cacerts/` 下 **149 / 149** 张证书的哈希都与自身文件名精确吻合。请注意它与新版 OpenSSL 的 `openssl x509 -subject_hash` **不同**（后者对规范化后的名称做 SHA-1）；若照搬会导致文件名静默出错。

若你的证书 Subject 与系统库中已有证书（或此前导入的证书）冲突，`n` 会自动递增——因此多个 Subject 相同的 keybox 不会互相覆盖。

| 现象 | 可能原因 | 处理 |
|---|---|---|
| 显示「已导入，尚未生效」 | 模块尚未挂载，或还没重启 | 启用模块并重启 |

## 常见问题

**Q：装了这个能过 Play Integrity 吗？**
不能。它只让**你的设备**在本地信任该根。Google 在服务端验证。能否通过取决于你的 keybox 是否真实、未被吊销。

**Q：我有真正的 Google 硬件 keybox，要装吗？**
不要。你的链本来就根植于受信任锚点，本模块毫无增益，也帮不了 Google 侧校验。

**Q：为什么还需要 TEE 模块？**
两者分工不同：TEE 模块负责**签发侧**（真的用这个 keybox 签链），本模块负责**信任侧**（让根被设备信任）。大多数 keybox 的根本来就被信任，此时并不需要本模块；只有根确实不受信任时，才需要用它补齐。

**Q：普通第三方 RKP keybox 需要装吗？**
通常**不需要**。多数设备已信任 Google 的 RKP 根，链本来就能验证通过。只有你的固件缺少该根（如部分非 GMS 或深度定制系统）、或该 keybox 使用私有 CA 链时才有帮助。

**Q：反复选择文件会堆积重复证书吗？**
不会。每次导入都先删除此前导入的 CA 文件。

**Q：可以完全还原吗？**
可以。停用/卸载模块即移除挂载与文件，重启后恢复原状。注意：**更新**模块会重置模块目录，更新后需重新选择一次 keybox。

**Q：会修改系统分区吗？**
不会。所有内容位于 `/data/adb/modules/AnyKeybox_module/`，由 root 管理器在开机时挂载。

**Q：支持哪些 Android 版本？**
实践上 Android 10+；APEX conscrypt 信任库为 Android 14+。较老设备走传统 `/system/etc/security/cacerts` 路径。
